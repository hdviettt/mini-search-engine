Outage report · 5 September 2026

Crawling stopped, and why the whole engine went with it

Railway project mini-search-engine. Diagnosed, fixed and deployed — 54360d9 → 8f4b91e, seven commits.

Production is serving again, and measurably better than its previous best.

No data was lost — 5,022 pages, 200,260 terms, 3.44 M postings, 61,364 chunks. Search is back to sub-second, and the evaluation against the frozen baseline moved from 0.7394 to 0.9101 nDCG@10. One thing is still open and it needs you: app sleeping is still enabled on the Postgres service.

Still to do, dashboard only. Railway → mini-search-engine → Postgres → Settings → turn off App Sleeping. There is no CLI or config-as-code path for a database service, so I could not do this one. Until it is off, Postgres keeps being hard-killed and crash-recovered every few minutes, and requests that land during a recovery window will still fail.

What actually happened

  1. App sleeping was enabled on the Postgres service Designed for stateless web services: when inbound HTTP traffic stops, Railway stops the container. Database clients speak raw TCP on 5432, so the signal Railway watches is not the signal that matters.
  2. Postgres was hard-killed, not shut down database system was not properly shut down, and a stale postmaster.pid removed on each boot. Every wake ran crash recovery.
  3. During recovery it refused connections FATAL: the database system is starting up. In-flight connections died mid-query — that is where SSL error: unexpected eof while reading came from. A symptom, not the disease.
  4. The backend restarted too, and replayed every overdue schedule at once load_from_db floored past-due schedules to max(1.0, remaining), so all of them fired within the same second of boot.
  5. Two concurrent crawls deadlocked on terms, and crawling stopped The crawl died one page in. pages.crawled_at had not moved since 18:15:13 on 4 September.

Findings and what was done

01The indexer deadlocked against itselfFixed

The fault that stopped crawling. index_page upserted terms in unsorted Counter order, which is page-dependent, and ON CONFLICT DO UPDATE SET term = EXCLUDED.term takes an exclusive row lock even though the write is a no-op. Two football pages share vocabulary, so they took the same locks in opposite orders.

backend/indexer/indexer.py

-    for term in all_counts:
+    for term in sorted(all_counts):

Verified against a restored copy of the index rather than argued from first principles — two threads presenting the same vocabulary in different orders, with and without the fix:

PRE-FIX (iterate page order): pageA=ok, pageB=DEADLOCK POST-FIX (iterate sorted) : pageA=ok, pageB=ok
02The scheduler guaranteed the collisionFixed

Finding 01 needed two crawls running at the same instant, and this made that certain rather than occasional: every overdue schedule fired one second after boot, together. Both default schedules started at 18:15:08. Because the database kept restarting, the backend kept restarting, and both were always overdue.

Overdue schedules are now staggered; a Postgres advisory lock guards the whole build path so two crawls can never write the index concurrently regardless of timing; and a deadlock is retried with backoff instead of ending the run. The skip path deliberately falls through to the reschedule — returning early there would have silently retired the schedule forever.

03The pool served dead connectionsFixed

No check, no max_lifetime. After a Postgres restart the pool kept its dead sockets and handed them to requests, producing the SSL error: unexpected eof while reading traceback. check_connection validates before handing over, for one round trip, and turns that into a transparent reconnect. This is why search works today despite the restart loop still running.

04Startup hung for 6.5 minutes instead of erroringFixed

get_connection() passed no connect_timeout and DATABASE_URL set none, so an unreachable host burned the OS TCP timeout — measured at 130 seconds per attempt, three times in sequence at boot. That is why uvicorn appeared to freeze on "Waiting for application startup." Local startup is now 3 seconds.

05The health check could not failFixed

/health was return {"status": "ok"} — a literal, on a service whose only real dependency is Postgres. It reported healthy through a day of 500s, which is why this was found by hand rather than by an alert. It now runs SELECT 1 and returns 503 on failure.

/health/live was added for liveness and never touches the database. Railway's healthcheck points there deliberately: restarting the API does not fix a broken database, it only adds a crash loop to the outage. /health is for external uptime monitoring — which is the thing that should actually page you, and is worth setting up.

06PageRank was ranking Wikipedia's furnitureFixed

Not part of the outage, found in the same logs. The most authoritative pages in the index were Help:Category, Wikipedia:Protection policy and File:Commons-logo.svg; "Association football" was fourth. The depth<=1 shortcut admitted any /wiki/ URL, and every article links to those namespaces, so they collected in-degree from the whole corpus.

Removing the namespaces alone was not enough — the citation-identifier articles moved straight into the vacancy, and the top five became Digital object identifier, ISBN, ISSN, Wayback Machine and OCLC. Those live in the article namespace, so they are matched by exact title. Both filters now apply at every depth, and scripts/purge_wiki_meta.py cleaned the pages crawled before they existed: 169 pages, 24,594 links and 6,460 queued URLs.

07Postgres app sleepingNeeds you

The root cause of the instability, and the only finding still open. A database service has no repository, so config-as-code cannot reach it and there is no CLI command — it is a dashboard toggle. The backend now pins sleepApplication: false in backend/railway.json; Postgres still reads true, and its logs still show the stop/start cycle.

08Schema drift, and stale backupsOpen

Two things worth knowing, neither urgent.

Production carries three tables this repository does not define — page_entities, entity_attributes, entity_relationships. The purge script found them the hard way, by failing on a foreign key it had never heard of. CLAUDE.md says the schema lives only in db.py; right now that is not true.

And the local database was genuinely deleted — the README's docker run had no -v, so the data lived in the container layer. It has been restored from full_backup.sql onto a named volume, and the README is fixed. But both dumps are gitignored, dated 16 March, and exist as one copy on one disk. Worth copying somewhere else.

The one regression

Misspelled queries fell 0.6218 → 0.5707, driven almost entirely by premeir league going 0.631 → 0.000. This is defect 3 in your own notes, not a new fault: spell correction is wired to /api/search/explain but never runs on /api/search, so the query searches the single stem leagu and which league pages surface was always luck. The purge changed the luck. Fixing defect 3 is the way to move that number — it is the obvious next piece of work, and it would likely take misspelled from 0.57 to something near the others.
