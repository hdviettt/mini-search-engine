3. The scrollbars

One cause, and it only shows above 1280px, which is why it seemed to be everywhere for you and nowhere in the code. html carries zoom: 1.2 above 1280px and 1.3 above 1600px. zoom scales rendered output but does not rescale viewport units, so 100vh resolves to the full viewport in CSS pixels and is then multiplied by the zoom. body was min-h-screen.

Measured with Playwright on the deployed site, four viewports, before any change:

ViewportzoomPage overflowArithmetic
1280 x 8001.2160px800 x 1.2 − 800
1728 x 10001.3300px1000 x 1.3 − 1000
1100 x 80010pxno zoom, no overflow

So every page at desktop width carried a page scrollbar that scrolled nothing, sitting a few pixels from the results list's own scrollbar. That is the two bars at the right edge in your screenshot. At 1100px, where no zoom applies, there was correctly only ever one.

The fix

--vph is now the viewport height already divided by the zoom in force. A pure-CSS fallback per breakpoint in globals.css, overridden before first paint from the measured window.innerHeight in layout.tsx, so it is also correct on browsers that do rescale vh under zoom and on mobile when the URL bar shows or hides. Every 100vh, h-screen and min-h-screen in the app is now var(--vph), and the local copy of this workaround that already existed in page.tsx is gone in favour of the global one.

4. A deploy failure the healthcheck caught

04A leaked connection was blocking startupFixed

The first deploy of this work failed, and it was right to. The healthcheck added in the previous session finally had something to catch, and what it caught had probably been true for a long time.

Attempt #4 failed with service unavailable 1/1 replicas never became healthy! ... INFO: Waiting for application startup. <- and never finishes

pg_stat_activity said why:

pid 36012 idle in transaction 15m56s SELECT c.id, c.page_id, ... pid 36225 active Lock/relation 13m28s ALTER TABLE postings ... pid 36239 active Lock/relation 6m54s CREATE TABLE IF NOT EXISTS ...

/api/overview/stream held a pooled connection for the whole Server-Sent Events response. psycopg opens a transaction on the first statement and holds it until the block exits, so the retrieval SELECT kept its locks for as long as the stream lived, which with a failing LLM call and a client that walked away was sixteen minutes. init_db()'s ALTER TABLE needs ACCESS EXCLUSIVE, so it queued behind it and startup never finished.

Note the shape of it: a zero-downtime deploy cannot recover from this on its own, because the leaked connection belongs to the old container and the old container is not retired until the new one is healthy. Three changes break it.

  • init_db() sets lock_timeout = 10s and statement_timeout = 60s. Both blocks already tolerate not applying, the schema is unchanged on nearly every boot, and a migration that cannot get its lock will get it next time. Startup must never be able to block forever on a lock.
  • streaming_conn() runs the SSE connection in autocommit, so each statement releases its locks immediately and an abandoned stream cannot block DDL again.
  • healthcheckTimeout 60s to 300s, which left no room for the schema migration against a cold Postgres.

Verified after redeploy: four sessions, all idle on Client, oldest 38 seconds. No idle in transaction, nothing waiting on a lock.
